# 커밋 스킬

변경 사항을 분석하고 ForDay 커밋 컨벤션에 맞는 커밋을 생성한다.

## 실행 순서

1. `git status`와 `git diff`를 실행해 변경된 파일과 내용을 파악한다.
2. 현재 브랜치명에서 이슈번호를 추출한다. (예: `fix/#341-record-hobby-create` → `#341`)
   - 브랜치명에 이슈번호가 없으면 `git log -5 --oneline`로 최근 작업 맥락을 확인한 뒤 사용자에게 이슈번호를 물어본다. 임의로 지어내지 않는다.
3. 변경의 성격을 분류해 prefix를 결정한다:
   - `feat` — 새로운 기능 추가
   - `fix` — 기능 수정
   - `chore` — 설정 / 환경 구성
   - `bug` — 오류 수정
   - `hotfix` — 긴급 수정
   - `refactor` — 코드 리팩토링
   - `docs` — 문서 작업
   - `test` — 테스트 코드 작성
   - `setting` — 세팅 관련 코드
   - `deploy` — 배포 관련 코드
4. 커밋 메시지를 아래 형식으로 작성한다. 요약은 한국어로 쓴다:
   ```
   [#이슈번호] prefix: 작업내용
   ```
   예: `[#341] feat: hobbyName으로 새 취미 생성 후 기록하는 기능 추가`

   영향 범위가 넓거나 이유 설명이 필요하면 본문을 추가한다:
   ```
   [#이슈번호] prefix: 작업내용

   - <상세 내용 1>
   - <상세 내용 2>
   ```
5. 관련 파일을 스테이징(`git add`)하고 커밋한다.
6. 커밋 결과를 출력한다.

## 규칙

- 하나의 커밋은 하나의 목적만 담는다. 성격이 다른 변경이 섞여 있으면 사용자에게 분리 여부를 먼저 물어본다.
- 시크릿·바이너리 파일은 절대 스테이징하지 않는다. 특히 `src/main/resources/application.yml`, `application-prod.yml`, `forday-*-firebase-adminsdk-*.json`은 `.gitignore` 대상이므로 `git add -f` 등으로 강제 추가하지 않는다.
- `.claude/settings.local.json`도 커밋하지 않는다.
- `--no-verify` 등 훅 우회 옵션은 사용하지 않는다.
- 기본 브랜치(`dev`)에 직접 커밋하지 않는다. `dev`에 있는 상태라면 먼저 `prefix/#이슈번호-설명` 형식의 브랜치를 만들지 사용자에게 확인한다.

## 실행

위 순서대로 바로 실행한다. 사용자에게 메시지 초안을 먼저 보여주고 확인받은 뒤 커밋한다.
