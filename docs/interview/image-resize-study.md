# 이미지 리사이징 면접 학습 자료

> 대상 사례: "기록에 사진을 여러 장 올리면 서버가 메모리 부족으로 죽던 문제 — 리사이징을 서버 밖으로 옮기기까지"
> 근거: `ForDay_Backend`, `ForDay_Infra`, `ForDay_GitOps` 작업 트리(2026-09-30 기준), `docs/perf/results/image-resize/`
> 표기: `클래스명:줄번호`. 전체 경로는 아래 "파일 색인" 참고.
> 알림 사례용 프롬프트 틀을 이 사례에 맞게 바꿨다. 알림 사례 자료는 `notification-pipeline-study.md`.

## 1분 요약

> 기록 하나에 사진을 최대 5장 올릴 수 있습니다. 리사이징을 API 서버가 요청 안에서 직접 하면 어떻게 되는지, 운영과 같은 t3.small EC2를 따로 띄워 휴대폰 사진 크기(4032×3024, 6.1MB) 5장으로 재현했습니다. 요청 하나는 4.4초 걸렸고, 초당 1건만 넣어도 31건 중 26건이 `OutOfMemoryError`로 죽었습니다.
>
> 원인은 파일 크기가 아니라 압축을 푼 크기였습니다. 6.1MB JPEG를 풀면 픽셀 데이터만 약 37MB이고, 실제 로그에서 실패한 할당도 정확히 그 크기였습니다. 자바 힙 한도는 약 478MB라 동시에 몇 건만 겹쳐도 넘쳤고, CPU도 두 코어가 45초 동안 가득 찼습니다.
>
> 그래서 리사이징을 서버 프로세스 밖으로 뺐습니다. 클라이언트가 presigned URL로 S3에 직접 올리면, S3 업로드 이벤트가 Lambda를 비동기로 호출해 썸네일을 만듭니다. 실패는 기본 재시도 두 번 뒤 SQS DLQ에 남기고 CloudWatch 알람으로 봅니다. 이미지 바이트는 이제 API 서버를 한 번도 거치지 않습니다.

# 1부. 기초 개념

각 항목: **정의 → 왜 필요한가 → 이 프로젝트에서**

### 1-1. 이미지 디코딩과 "파일 크기 ≠ 메모리 크기"

- **정의**: JPEG는 압축된 형식이다. 리사이즈하려면 먼저 픽셀 배열로 풀어야(디코딩) 하고, 그 크기는 대략 가로 × 세로 × 픽셀당 바이트(RGB면 3)다.
- **왜 중요한가**: 메모리를 차지하는 건 파일이 아니라 풀린 픽셀 배열이다. 같은 해상도면 파일이 1MB든 6MB든 풀린 크기는 같다.
- **이 프로젝트**: 4032 × 3024 × 3 = **36,578,304바이트(약 36.6MB)**. 실측 로그의 실패 메시지 `Retried waiting for GCLocker too often allocating 4572290 words`에서 4,572,290 워드 × 8바이트 = **36,578,320바이트** — 정확히 한 장을 풀 때의 배열 하나다(`perf-app-full.log`). 여기에 원본 바이트 배열(6.1MB, `SyncImageResizeMeasurementService:53-60`)과 출력 버퍼, Thumbnailator 내부 버퍼가 더해진다.

### 1-2. JVM 힙과 최대 힙 크기(`-Xmx`)

- **정의**: 자바 객체가 사는 메모리 영역이 힙이다. `-Xmx`로 최대 크기를 정한다. 안 정하면 JVM이 가용 메모리를 보고 정한다(컨테이너 인식, 기본 25% — 기본값, JDK 문서로 확인 권장).
- **왜 중요한가**: 힙이 모자라면 GC가 계속 돌며 CPU를 쓰다가 결국 `OutOfMemoryError`를 던진다.
- **이 프로젝트**: 측정 컨테이너는 메모리 제한도 `-Xmx`도 없어서, JVM이 호스트 메모리 1.866GiB를 보고 `MaxHeapSize = 501,219,328바이트`(약 478MiB)로 잡았다(측정 중 `java -XX:+PrintFlagsFinal`로 확인). 501,219,328 ÷ 1.866GiB = **25.0%** — JVM 기본 비율(`MaxRAMPercentage` 25)과 일치한다. 운영(k3s)은 `values.yaml`의 `javaOpts: "-Xmx512m"`를 `JAVA_TOOL_OPTIONS` 환경변수로 넣고(`forday-app templates/rollout.yaml:46-47`), 컨테이너 limit은 768Mi다(`values.yaml:10-20`).

### 1-3. 힙 한도와 컨테이너 메모리(RSS)는 다르다

- **정의**: `docker stats`의 메모리는 프로세스 전체 사용량(힙 + 메타스페이스 + 스레드 스택 + 코드 캐시 등)이다. 힙 한도는 그중 자바 객체 영역의 상한이다.
- **이 프로젝트**: 부하 중 컨테이너 메모리는 785→856MB로 **호스트 한도(1.87GB)의 절반도 안 됐는데** OOM이 났다. 컨테이너가 아니라 **힙 478MB가 먼저 찬 것**이다. "메모리 856MB인데 왜 OOM이냐"는 질문의 답이 이 구분이다.

### 1-4. GC와 GC Locker

- **정의**: GC는 안 쓰는 객체를 치워 힙을 확보한다. 큰 배열을 한 번에 할당하려는데 공간이 없으면 GC를 돌리고 재시도한다. GC Locker는 네이티브 코드가 힙 배열을 붙잡는 동안 GC를 잠시 막는 장치다.
- **이 프로젝트**: 로그의 `Retried waiting for GCLocker too often` 경고는 37MB 배열 할당이 GC를 기다리며 여러 번 재시도하다 실패했다는 뜻이다(JPEG 디코더가 네이티브 코드를 쓰는 구간과 겹친 것으로 보인다 — 추정). 그 직후 해당 스레드들이 `OutOfMemoryError`로 500을 냈다.

### 1-5. CPU 바운드 작업과 요청 스레드

- **정의**: 디코딩·축소·재인코딩은 대기 없이 CPU만 쓰는 작업이다. 톰캣 요청 스레드가 이걸 하면 그 시간만큼 스레드와 코어를 점유한다.
- **이 프로젝트**: t3.small은 vCPU 2개다. 부하 동안 컨테이너 CPU가 161~198%로 약 45초 고정(`stats-rate1.log`). 요청 하나(5장)가 4.42초 걸리는데 초당 1건이 들어오면 처리가 유입을 못 따라가 동시 처리 건수가 계속 늘고, 그만큼 힙에 풀린 이미지가 동시에 올라간다.

### 1-6. Presigned URL

- **정의**: 서버가 자기 자격증명으로 서명해 발급하는, 특정 객체에 대한 **임시 업로드(PUT) 권한 URL**. 클라이언트는 AWS 자격증명 없이 이 URL로 S3에 직접 올린다.
- **왜 필요한가**: 이미지 바이트가 API 서버를 거치지 않는다(서버 대역폭·메모리 절약). 서버는 권한만 발급한다.
- **이 프로젝트**: `POST /app/presign`(`AppController`) → `AppService:61-76` → `S3ImageStorageAdapter:56-64` → `S3Service:28-50`(키 생성, `{usage}/temp/{uuid}_{파일명}`) + `:63-75`(PUT, 만료 5분 `:78`, Content-Type 서명). 서명은 네트워크 호출 없이 로컬에서 계산된다.

### 1-7. S3 이벤트 알림과 Lambda 비동기 호출

- **정의**: S3에 객체가 생기면(ObjectCreated) 이벤트를 Lambda·SQS·SNS로 보낼 수 있다. Lambda는 이 이벤트를 **비동기(Event) 호출**로 받는다 — S3는 결과를 기다리지 않고, Lambda 서비스가 내부 큐에 넣고 실행한다.
- **비동기 호출의 재시도**: 함수가 실패하면 Lambda가 기본 **2번 더** 재시도한다(총 3회). 그래도 실패하면 이벤트를 버리거나, 설정된 실패 대상(Destination)으로 보낸다(기본값 — AWS 문서로 확인 권장).
- **이 프로젝트**: `lambda_sqs.tf:3-5` 주석(S3 → 비동기 호출, 기본 2회 재시도). **S3 이벤트 알림 설정과 함수 코드는 콘솔에서 만들어져 Terraform이 관리하지 않는다** — 함수는 데이터 소스로만 참조(`lambda_data.tf:1-7`). 함수 설정은 state 기준 Node.js 20.x, 메모리 512MB, 타임아웃 50초.

### 1-8. DLQ와 Lambda Destinations

- **정의**: 처리에 끝내 실패한 메시지를 따로 보관하는 큐. Lambda 비동기 호출에서는 `on_failure` Destination으로 SQS를 지정할 수 있다.
- **왜 필요한가**: 없으면 재시도 후 이벤트가 조용히 사라진다. 사용자에게는 깨진 썸네일로만 드러난다(`lambda_sqs.tf:4-5`).
- **이 프로젝트**: `forday-image-resize-dlq`, 보관 14일(SQS 최대값, `lambda_sqs.tf:8-13`), `aws_lambda_function_event_invoke_config`로 연결(`:35-45`). **DLQ에 쌓인 이벤트를 다시 처리하는 코드나 절차는 없다** — 알람으로 알고 사람이 처리한다.

### 1-9. CloudWatch 알람

- **이 프로젝트**(`lambda_cloudwatch_alarms.tf`): Errors 합계 ≥ 임계값(5분, `:4-22`), Throttles ≥ 1(`:24-42`), Duration p99 > 임계값 3회 연속(`:44-62`), DLQ 메시지 ≥ 1(`:64-81`).
- **알림 경로**: 알람 → SNS 토픽 `lambda_alarms`(`lambda_sns.tf:1`) → 구독(`lambda_sns.tf:5`) → Discord 중계 Lambda(Python 3.12, `lambda_discord_relay.tf:31-36`, SNS 호출 권한 `:49-54`) → Discord 웹훅. 중계 Lambda는 코드까지 Terraform이 관리한다(리사이즈 함수와 대조).

### 1-10. Lambda 버전과 별칭(alias)

- **정의**: 버전은 특정 시점 코드의 불변 스냅샷, 별칭은 버전을 가리키는 이름표. 호출자가 별칭을 부르면, 별칭이 가리키는 버전만 바꿔 즉시 롤백할 수 있다. 함수 이름만 부르면 항상 `$LATEST`다.
- **이 프로젝트**: 리사이즈 함수에 `prod` 별칭을 만들었다(`lambda_alias.tf:10-19`). 하지만 **S3 트리거는 $LATEST를 호출한다**(`lambda_sqs.tf:34`). 앱에서 별칭을 쓰는 곳은 커버 생성 Lambda 호출뿐이다(`CoverLambdaInvoker:33-48`, 다른 함수). 즉 **리사이즈 경로에서는 별칭 롤백이 동작하지 않는다.** 되게 하려면 S3 알림의 대상 ARN을 `함수명:prod`로 바꿔야 한다.

### 1-11. 결과적 일관성(eventual consistency)과 썸네일 URL

- **정의**: 업로드 직후에는 썸네일이 아직 없고, 조금 뒤에 생긴다.
- **이 프로젝트**: 서버는 썸네일이 생겼는지 확인하지 않고 원본 URL의 `/temp/`를 `/resized/thumb/`로 바꿔 돌려준다(`ImageUrlConverter:24-37`, 피드 `GetActivityRecordByStoryResDto:55`). 업로드 직후 피드를 보면 썸네일이 아직 없어 이미지가 깨질 수 있다. 서버 쪽 대비 코드는 없다(클라이언트가 원본으로 대체하는지는 확인 필요).

### 1-12. 테스트 경로 분리(`TEST_` usage)

- **이 프로젝트**: `ImageUsageType`에 `TEST_ACTIVITY_RECORD`가 있고, `S3Service:33-44`가 이를 `test_activity_record/temp/` 경로로 만든다. 측정은 이 경로만 썼다 — 실제 `activity_record/temp/`에 올리면 운영 Lambda가 같은 파일을 또 리사이즈해 운영 지표가 오염된다(`SyncImageResizeMeasurementService` 클래스 주석). 측정 EC2의 S3 권한도 `test_activity_record/*`로 좁혔다(`perf_test.tf:143-171`). 트리거가 `test_` 경로를 무시한다는 건 콘솔 설정이라 코드로는 확인할 수 없다.

### 1-13. EC2 인스턴스 메타데이터와 IMDSv2 홉 제한

- **정의**: EC2 안에서 `169.254.169.254`로 인스턴스 역할 자격증명 등을 얻는다. IMDSv2는 토큰이 필요하고, 응답 홉 제한이 1이면 도커 브리지를 거친 컨테이너는 토큰을 받지 못한다.
- **이 프로젝트**: 측정 앱은 정적 키 대신 인스턴스 역할로 S3에 접근했다(`MeasureS3Config:28-39`, `InstanceProfileCredentialsProvider`). 기본 자격증명 체인은 `.env`의 더미 `AWS_ACCESS_KEY`를 먼저 집어서(레거시 환경변수 이름 인식) 쓰지 않았다(`MeasureS3Config` 주석). 홉 제한은 이미 2였다(`perf_test.tf:193-196`에 명시).

### 1-14. k6 `constant-arrival-rate`

- **정의**: 서버 응답과 무관하게 정해진 속도로 요청을 넣는다. 서버가 못 따라가면 VU가 늘어난다.
- **이 프로젝트**: 격리 측정은 초당 1건, 30초, VU 20~100(`image-resize-sync-isolated.js:40-50`). 30건 도착 예정에 31건 발행, **`dropped_iterations` 0건**(`results-rate1.json`에 항목 없음) — k6는 예정대로 모두 보냈고, 실패는 전부 서버 쪽(500)이다.

# 2부. 코드 흐름 따라가기

### 2-1. 현재 운영 흐름 (Lambda)

| 순서 | 누가 | 코드 / 설정 | 서버 자원 사용 |
| --- | --- | --- | --- |
| 1 | 앱 | `POST /app/presign` (이미지 N개 정보) | 요청 스레드, 서명 계산만 |
| 2 | 서버 | `AppService:61-76` → `S3ImageStorageAdapter:56-64` 키·PUT URL 생성(5분) | CPU 수 ms |
| 3 | 앱 | 각 URL로 S3에 **직접 PUT** | **서버 관여 없음** |
| 4 | S3 → Lambda | ObjectCreated 이벤트 → 리사이즈 함수 **비동기** 호출($LATEST) | 서버 관여 없음 |
| 5 | Lambda | 원본 읽기 → 리사이즈 → `/resized/...`에 저장. 실패 시 2회 재시도 → DLQ | 서버 관여 없음 |
| 6 | 앱 | `POST /api/v2/records` (이미지 URL, 순서, **가로·세로는 클라이언트가 보냄**) | 요청 스레드 |
| 7 | 서버 | `ActivityRecordServiceV2:126-155` 기록 저장, `:151-152` 이미지 행 저장(첫 장이 썸네일, `:273-278`) | DB 쓰기만 |
| 8 | 앱 | 피드 조회 → 서버가 `/temp/`→`/resized/thumb/` 문자열 치환해 응답 | 바이트 처리 없음 |

- **서버가 죽으면**: 서버가 이미지 처리를 하지 않으므로 리사이즈는 영향이 없다. 4~5번은 AWS가 처리한다.
- **리사이즈가 실패하면**: 2회 재시도 후 DLQ에 남고 알람이 울린다. 썸네일 URL은 이미 응답에 나가므로 사용자는 깨진 이미지를 본다.
- **6번과 4~5번은 독립**이다. 기록 저장이 먼저 끝날 수도, 리사이즈가 먼저 끝날 수도 있다.

### 2-2. 측정용 "서버가 리사이즈했다면" 흐름

| 순서 | 스레드 | 코드 | 메모리 |
| --- | --- | --- | --- |
| 1 | 톰캣 요청 스레드 | `TestImageResizeMeasurementController:22-24` | |
| 2 | 같음 | `SyncImageResizeMeasurementService:45-51` 키 5개를 **순서대로** 처리 | |
| 3 | 같음 | `download` `:53-60` — S3 GetObject → `readAllBytes()` | 원본 6.1MB 배열 |
| 4 | 같음 | `resize` `:62-73` — `Thumbnails.of(...).width(400).outputFormat("jpg")` | **디코딩 약 36.6MB** + 축소본 + 출력 |
| 5 | 같음 | `upload` `:75-80` — PutObject(`/resized/thumb/`) | 수 KB |
| 6 | 같음 | 5장 끝나면 200 반환 | |

- 한 요청 안에서는 한 번에 한 장만 풀린다. 문제는 **요청이 겹칠 때**다. 요청 하나가 4.42초 걸리는데 초당 1건이 들어오면 최소 4~5건이 겹치고, CPU가 포화되면 처리 시간이 늘어 겹치는 건수가 더 늘어난다. 동시 5~10건 × 약 45MB가 앱 자체 힙 사용량 위에 더해지면 478MB를 넘는다.
- 이 흐름에는 DB 저장이 없다. "서버가 리사이즈하는 비용"만 떼어 보려고 일부러 뺐다(클래스 주석).
- S3 클라이언트는 측정 전용 빈(`MeasureS3Config`, `@Primary`)이다.

# 3부. 고려한 상황과 경계 사례

### 3-1. Lambda가 리사이즈에 실패하면?

- **경로**: 비동기 호출 실패 → Lambda가 기본 2회 재시도 → 여전히 실패하면 `on_failure` Destination인 SQS로 이벤트 전송(`lambda_sqs.tf:35-45`) → `dlq-not-empty` 알람(`lambda_cloudwatch_alarms.tf:64-81`).
- **사용자 영향**: 기록은 이미 저장됐고 썸네일 URL도 응답에 포함된다. 썸네일 파일이 없어 깨진 이미지가 보인다.
- **현재 한계**: DLQ를 다시 처리하는 도구가 없다. 재처리는 사람이 해야 한다.
- **개선하려면**: DLQ 메시지를 원본 키로 다시 Lambda에 넣는 재처리 스크립트나 SQS → Lambda 재구독, 클라이언트에 원본 대체 표시.

### 3-2. 업로드 직후 썸네일을 요청하면?

- **경로**: 서버는 썸네일 존재를 확인하지 않고 URL만 바꿔 준다(`ImageUrlConverter:32-37`).
- **결과**: 리사이즈가 끝나기 전이면 S3가 403/404를 준다(버킷 정책에 따라 다름 — 확인 필요).
- **현재 한계**: 서버 쪽 대비 없음.
- **개선하려면**: 클라이언트가 실패 시 원본 URL로 대체, 또는 Lambda 완료를 DB에 기록해 완료 전에는 원본 URL을 주기.

### 3-3. 같은 이벤트가 두 번 오면(중복 호출)?

- **경로**: S3 이벤트 알림과 Lambda 비동기 호출은 최소 한 번 전달이라 드물게 중복 호출될 수 있다.
- **결과**: 리사이즈는 같은 입력에서 같은 출력 키(`/resized/thumb/...`)에 덮어쓰므로 **결과가 같다(멱등).** 비용만 조금 더 든다.
- **현재 한계**: 없음(Lambda 코드가 저장소에 없어 출력 키 규칙은 `ImageUrlConverter`의 규약으로만 확인 가능).

### 3-4. 클라이언트가 아주 큰 파일이나 이미지가 아닌 파일을 올리면?

- **경로**: presigned PUT에는 Content-Type만 서명되고(`S3Service:73`), **크기 제한이 없다.** 서버는 파일 내용을 보지 않는다.
- **결과**: 거대한 이미지는 Lambda 메모리(512MB)·타임아웃(50초)을 넘겨 실패 → DLQ. 서버는 영향 없음(분리의 효과).
- **현재 한계**: 업로드 크기 검증 없음, 기록 생성 시 `validateExists`류 확인은 있으나(`S3ImageStorageAdapter:67-77`) 크기·형식 검증 없음.
- **개선하려면**: presigned **POST** 정책의 `content-length-range`로 크기 제한, Lambda에서 형식 확인 후 거부.

### 3-5. 기록 하나에 5장보다 많이 올리면?

- **경로**: `POST /api/v2/records`의 `ActivityRecordReqDtoV2:36-38`에는 `@Valid`와 설명만 있고 `@Size`가 없다. presign 요청 개수도 제한이 없다(`AppService:61-76`).
- **결과**: 서버는 6장 이상도 받는다. 5장은 앱이 지키는 규칙일 뿐이다.
- **개선하려면**: `@Size(max = 5)` 추가. 이미 만들어진 `RecordActivityReqDtoV2:17`은 쓰이지 않는다.

### 3-6. 트래픽이 몰려 Lambda가 동시에 많이 뜨면?

- **경로**: Lambda는 요청마다 실행 환경을 늘린다. 계정·함수 동시성 한도를 넘으면 스로틀.
- **결과**: 비동기 호출의 스로틀은 Lambda가 일정 시간(기본 최대 6시간) 재시도한다(기본값 — 확인 권장). `throttles` 알람이 울린다. API 서버는 영향 없음.
- **현재 한계**: 예약 동시성 설정 없음(Terraform에 없음).
- **개선하려면**: 예약 동시성으로 상한을 두어 S3 GET 비용·다운스트림 폭주 제어.

### 3-7. 새 리사이즈 코드에 버그가 있으면 되돌릴 수 있나?

- **경로**: S3 트리거는 $LATEST(`lambda_sqs.tf:34`). `prod` 별칭(`lambda_alias.tf`)은 리사이즈 경로에서 쓰이지 않는다.
- **결과**: 지금은 **이전 코드를 다시 배포하는 것 말고는 되돌릴 방법이 없다.** 포트폴리오 문장과 다르다.
- **개선하려면**: S3 알림 대상을 `fordayImageResizeFunction:prod`로 바꾸고, 이벤트 호출 설정(DLQ)도 별칭 기준으로 다시 걸기, 버전 간 전환 리허설 기록.

### 3-8. 원본 파일은 언제 지워지나?

- **경로**: 기록 삭제 시 커밋 후 원본과 리사이즈본을 함께 지운다(`S3ImageStorageAdapter:79-129`). temp 경로 자동 만료 규칙은 정상 파일까지 지워서 **2026-09-17에 전부 제거했다**(`lambda_s3_lifecycle.tf:1-7`).
- **현재 한계**: presign만 받고 기록을 만들지 않은 업로드(고아 원본)는 영원히 남는다. 측정에서 올린 `test_activity_record/` 파일도 남아 있다.
- **개선하려면**: DB에 없는 temp 객체를 찾아 지우는 정리 배치.

### 3-9. 측정 환경 구성에서 겪은 문제 (면접에서 "어려웠던 점"으로 쓸 수 있음)

- 매 요청 32MB 업로드 → 발생기 EC2 네트워크 포화, SSH 불가 → 재부팅 후 원본을 한 번만 올리고 리사이즈만 반복하는 격리 측정으로 재설계(`image-resize-sync-isolated.js:8-18`).
- 기본 자격증명 체인이 `.env`의 더미 `AWS_ACCESS_KEY`를 먼저 집음 → 인스턴스 역할만 쓰도록 고정(`MeasureS3Config:28-39` 주석).
- 컨테이너에서 IMDS 접근 실패를 의심해 홉 제한을 확인 → 이미 2였음. `wget` 테스트가 토큰 없이 요청해 거짓 실패였고, `curl`로 토큰을 받아 정상 확인. **추측을 측정으로 바로잡은 사례**.

# 4부. 설계 선택과 대안

### 4-1. 서버 동기 처리 vs `@Async` vs Lambda

| | 서버 동기 | 서버 `@Async` | Lambda(선택) |
| --- | --- | --- | --- |
| API 응답 | 리사이즈 시간만큼 지연 | 빠름 | 빠름 |
| 서버 메모리·CPU | 요청마다 사용 | **여전히 같은 프로세스가 사용** | 사용 안 함 |
| 서버가 죽으면 | 요청 실패 | 큐의 작업 유실 | 영향 없음 |
| 확장 | 서버 증설 | 서버 증설 | 호출마다 자동 |
| 측정 | 초당 1건에 OOM 84% | **측정하지 않음(추론)** | 서버 부하 0 |
- **`@Async`를 뺀 근거는 측정이 아니라 추론이다.** 면접에서 "측정했나요?"에 "아니요, 연산이 같은 힙을 쓰므로 동시 처리 수만 실행자 크기로 제한될 뿐 같은 문제를 늦춘다고 판단했다. 스레드 수를 1~2로 제한하면 OOM은 막겠지만 대신 큐가 쌓인다"로 답할 것.

### 4-2. 다른 대안들

| 대안 | 장점 | 기각 이유 / 비용 |
| --- | --- | --- |
| 클라이언트에서 줄여서 올리기 | 서버·클라우드 비용 0, 업로드도 가벼움 | 앱 버전·기기마다 결과가 다름, 원본 보존과 여러 크기 생성이 어려움. **같이 쓰면 좋은 보완책** |
| 별도 워커 서버 + 큐 | 언어·라이브러리 자유, 비용 예측 쉬움 | 서버 하나 더 운영. 단일 EC2 시절엔 부담 |
| 요청 시점 변환(CloudFront + Lambda@Edge, imgproxy 등) | 크기를 자유롭게, 미리 만들 필요 없음 | 첫 요청 지연, 캐시·CDN 설정 필요. 피드처럼 정해진 크기에는 과함 |
| 서버 힙을 늘리기 | 코드 변경 없음 | 동시 요청 수에 비례해 늘 뿐 상한이 없음. CPU 포화는 그대로 |
| Lambda(선택) | 서버와 자원 완전 분리, 트래픽 없을 때 비용 0 | 콜드 스타트, 결과적 일관성(3-2), 코드가 저장소 밖(콘솔) |

### 4-3. Lambda 코드를 Terraform으로 관리하지 않은 것

- **선택**: 콘솔로 만든 함수를 데이터 소스로만 참조(`lambda_data.tf:1-3`). apply가 운영 함수를 덮어쓰지 않게.
- **비용**: 리사이즈 로직이 어떤 저장소에도 없다. 면접에서 "Lambda 코드 보여주세요"에 보여줄 수 없고, 리뷰·버전 관리가 안 된다. 개선: 함수 코드를 저장소로 가져와 `archive_file`로 배포(디스코드 중계 Lambda는 이미 그렇게 함).

### 4-4. DLQ 방식

- **Destination(on_failure) vs 함수 DLQ 설정**: Destination은 실패 이벤트와 함께 오류 정보(요청 ID, 응답)를 담는다. 함수 DLQ는 원본 이벤트만. 여기서는 Destination을 썼다(`lambda_sqs.tf:35-45`).

# 5부. 예상 면접 질문

## A. 기초

**Q1. 6MB 파일인데 왜 메모리가 그렇게 많이 드나요?**
> JPEG는 압축돼 있어서 리사이즈하려면 픽셀 배열로 풀어야 합니다. 4032×3024에 픽셀당 3바이트라 약 37MB입니다. 실제 실패 로그에도 정확히 36,578,320바이트짜리 배열 할당이 실패했다고 찍혀 있었습니다. 파일 크기가 아니라 해상도가 메모리를 결정합니다. (`perf-app-full.log`, `SyncImageResizeMeasurementService:62-73`)
- 꼬리: *파일이 1MB면요?* → 해상도가 같으면 풀린 크기는 같습니다. 그래서 파일 크기 제한보다 해상도 제한이 효과적입니다.

**Q2. 컨테이너 메모리가 856MB였는데 왜 OOM이 났나요?**
> 컨테이너 사용량은 힙 말고도 메타스페이스, 스레드 스택 같은 걸 다 합친 값이고, OOM은 자바 힙 한도에서 났습니다. 힙 한도가 약 478MB였습니다. (`PrintFlagsFinal` 결과, `stats-rate1.log`)
- 꼬리: *힙을 늘리면 해결되나요?* → 동시 요청이 늘면 다시 넘습니다. 상한이 없는 문제라 늘리는 걸로는 못 끝냅니다. CPU 포화도 그대로입니다.

**Q3. 478MB는 어디서 나온 숫자인가요?**
> 측정 컨테이너에 메모리 제한도 `-Xmx`도 없어서, JVM이 호스트 메모리 약 1.87GB의 기본 비율로 잡은 값입니다. 운영은 지금 `-Xmx512m`이라 비슷한 수준입니다. (`forday-app values.yaml:10-20`)

**Q4. presigned URL이 뭐고 왜 썼나요?**
> 서버가 서명해서 발급하는 임시 업로드 URL입니다. 클라이언트가 S3에 직접 올리니 이미지 바이트가 서버를 거치지 않습니다. 서버는 서명만 하고 네트워크 호출도 없습니다. 만료는 5분입니다. (`S3Service:63-79`, `S3ImageStorageAdapter:56-64`)
- 꼬리: *URL이 유출되면?* → 5분 안에 그 한 객체 키에만 올릴 수 있습니다. 대신 크기 제한이 없어서 POST 정책으로 바꾸는 게 개선점입니다.

**Q5. S3가 Lambda를 어떻게 부르나요?**
> 객체가 생기면 ObjectCreated 이벤트로 Lambda를 비동기 호출합니다. S3는 결과를 기다리지 않고, 실패하면 Lambda가 기본으로 두 번 더 재시도합니다. (`lambda_sqs.tf:3-5`)

**Q6. DLQ는 왜 두었나요?**
> 전에는 재시도 후 이벤트가 그냥 버려져서 서버도 클라이언트도 몰랐고, 사용자는 깨진 썸네일로만 알았습니다. 실패 이벤트를 SQS에 14일 보관하고, 하나라도 쌓이면 알람이 오게 했습니다. (`lambda_sqs.tf:4-13`, `lambda_cloudwatch_alarms.tf:64-81`)
- 꼬리: *쌓인 건 어떻게 다시 처리하나요?* → 지금은 자동 재처리가 없어 사람이 합니다. 재처리 스크립트가 다음 과제입니다.

**Q7. Lambda 버전과 별칭은 뭔가요?**
> 버전은 코드 스냅샷, 별칭은 버전을 가리키는 이름표입니다. 호출자가 별칭을 부르면 가리키는 버전만 바꿔 롤백할 수 있습니다.
- 꼬리: *그럼 리사이즈도 그렇게 롤백되나요?* → 솔직히 아닙니다. S3 트리거가 별칭이 아니라 $LATEST를 부르고 있어서, 별칭은 만들어만 둔 상태입니다. 트리거 대상을 별칭으로 바꿔야 합니다. (`lambda_sqs.tf:34`)

## B. 코드·측정

**Q8. 측정을 어떻게 설계했나요?**
> 운영 마이그레이션 전과 같은 t3.small EC2를 따로 띄우고 부하 발생기도 다른 인스턴스에 뒀습니다. 휴대폰 사진 크기인 4032×3024, 6.1MB 이미지 다섯 장을 S3 테스트 경로에 올려두고, 서버가 그걸 내려받아 리사이즈하고 다시 올리는 엔드포인트를 초당 1건씩 30초 호출했습니다. CPU·메모리는 docker stats로, 실패 원인은 앱 로그로 봤습니다. (`image-resize-sync-isolated.js`, `SyncImageResizeMeasurementService`)
- 꼬리: *왜 원본을 매번 새로 안 올렸나요?* → 처음엔 그렇게 했는데 요청마다 32MB를 올리다 보니 부하 발생기 네트워크가 먼저 막혀 SSH까지 끊겼습니다. 재려는 건 서버의 리사이즈 비용이라 업로드는 한 번만 하고 리사이즈만 반복했습니다.

**Q9. 원래 서버에서 리사이징했던 건가요?**
> 아닙니다. 이 프로젝트는 처음부터 Lambda로 리사이즈했습니다. "서버에서 했다면 어떻게 되는가"를 추측이 아니라 측정으로 보이려고 측정 프로파일에서만 켜지는 서버 리사이즈 경로를 새로 만들어 재현했습니다. (`@Profile("measure")`)

**Q10. 초당 1건이면 적은데 왜 무너졌나요?**
> 요청 하나가 4.4초라, 초당 1건이면 이미 4~5건이 동시에 돕니다. CPU 두 개가 가득 차면 각 요청이 더 느려지고 겹치는 수가 더 늘어납니다. 각 요청이 풀린 이미지 37MB 이상을 들고 있으니 힙 478MB를 금방 넘었습니다.

**Q11. 성공한 5건의 응답 시간은요?**
> 중앙값 약 21초, 최대 약 30초였습니다. 실패한 요청은 OOM으로 일찍 끝난 것도 있어서 전체 중앙값(약 9초)보다 성공한 요청이 오히려 더 느렸습니다. (`results-rate1.json` `expected_response:true`)

**Q12. 테스트 이미지는 진짜 사진인가요?**
> 아닙니다. 해상도와 파일 크기를 휴대폰 사진에 맞춘 합성 이미지입니다. 메모리 사용량은 해상도로 정해져서 측정 결론에는 영향이 없지만, 리사이즈 결과 파일 크기는 실제 사진과 다를 수 있습니다.

**Q13. 측정 환경에서 S3 권한은 어떻게 줬나요?**
> 정적 키 대신 EC2 인스턴스 역할을 썼고, 권한은 테스트 경로(`test_activity_record/*`)의 읽기·쓰기로만 좁혔습니다. 운영 이미지를 실수로라도 건드릴 수 없게요. (`perf_test.tf:143-171`, `MeasureS3Config`)
- 꼬리: *기본 자격증명 체인을 안 쓴 이유는?* → 컨테이너 환경변수에 더미 `AWS_ACCESS_KEY`가 있었는데, AWS SDK v1이 그 레거시 이름도 인식해서 인스턴스 역할보다 먼저 집었습니다. 인스턴스 역할만 쓰도록 고정했습니다.

**Q14. 왜 테스트 경로를 따로 썼나요?**
> 운영 경로에 올리면 운영 Lambda가 같은 파일을 또 리사이즈합니다. 측정 부하가 운영 Lambda 지표와 비용을 오염시킵니다. 코드에 이미 `TEST_` 경로 규칙이 있어서 그걸 썼습니다. (`S3Service:33-44`, `ImageUsageType`)

**Q15. 썸네일 URL은 서버가 어떻게 아나요?**
> 원본 URL의 `/temp/`를 `/resized/thumb/`로 바꾸는 문자열 규칙입니다. 서버가 파일이 있는지 확인하지는 않습니다. (`ImageUrlConverter:24-37`)
- 꼬리: *업로드 직후엔 썸네일이 없잖아요?* → 네, 그 사이엔 깨진 이미지가 보일 수 있습니다. 클라이언트가 원본으로 대체하거나, 리사이즈 완료를 기록해 두는 방식이 필요합니다.

**Q16. 기록당 5장은 어디서 막나요?**
> 솔직히 지금 기록 생성 API에서는 검증되지 않습니다. 요청 DTO에 설명만 있고 `@Size`가 없습니다. 앱이 막고 있는 규칙이라 서버에 `@Size(max = 5)`를 추가해야 합니다. (`ActivityRecordReqDtoV2:36-38`)

**Q17. 피드 트래픽이 122MB에서 111KB로 줄었다는 계산은?**
> 피드 기본 페이지 크기 20개 × 이미지 한 장씩으로 계산했습니다. 다만 111KB는 측정용 서버 코드가 400px로 줄인 합성 이미지 크기라, 실제 운영 Lambda가 만드는 썸네일 크기로 다시 계산해야 정확합니다. (`ActivityRecordController:117` 기본 size 20)

## C. 꼬리·압박

**Q18. `@Async`로 돌리면 되지 않나요?**
> 응답은 빨라지지만 연산은 같은 프로세스, 같은 힙에서 합니다. 스레드를 적게 두면 OOM은 피하지만 대신 작업이 큐에 쌓이고, 서버가 죽으면 큐가 사라집니다. 다만 이건 측정이 아니라 판단이라, 측정했다고는 말하지 않겠습니다.

**Q19. 서버 메모리를 늘리면 되지 않나요?**
> 동시에 처리하는 이미지 수만큼 메모리가 늘어나서 상한이 없습니다. CPU도 두 코어가 가득 찼기 때문에 메모리만 늘려도 응답 시간은 해결되지 않습니다. 이미지 처리량이 API 서버의 자원 예산에 묶이지 않게 떼는 게 맞다고 봤습니다.

**Q20. Lambda의 단점은?**
> 콜드 스타트로 첫 호출이 느리고, 업로드와 썸네일 생성 사이에 시간차가 생깁니다. 코드가 지금 저장소 밖에 있어 리뷰와 버전 관리가 안 되는 것도 문제입니다. 동시 실행 한도를 넘으면 스로틀이 걸리는데, 그건 알람으로 보고 있습니다.

**Q21. Lambda 코드를 보여줄 수 있나요?**
> 지금은 못 보여드립니다. 콘솔에서 만든 함수라 Terraform도 데이터 소스로만 참조하고 코드를 관리하지 않습니다. 운영 중 함수를 실수로 덮어쓰지 않으려는 선택이었는데, 결과적으로 코드가 저장소 밖에 남았습니다. 개선 과제입니다. (`lambda_data.tf:1-7`)

**Q22. 리사이즈가 중복 실행되면요?**
> 같은 원본에서 같은 출력 키로 덮어써서 결과가 같습니다. 멱등이라 비용만 조금 더 듭니다.

**Q23. 이 측정 결과를 운영에 그대로 적용할 수 있나요?**
> 결론은 적용됩니다. 운영 힙이 512MB라 측정의 478MB와 비슷하고, 해상도가 같으면 풀린 크기도 같으니까요. 다만 한 번의 30초 측정이고, 초당 1건 한 가지 부하만 봤습니다. "몇 건부터 무너지는가"를 찾으려면 부하를 단계별로 바꿔 더 재야 합니다.

**Q24. 99.91% 감소는 어떻게 쟀나요?**
> 원본 6.11MB와 리사이즈 결과 5.54KB를 S3에서 직접 확인했습니다. 그런데 그 결과는 측정용 서버 코드가 만든 파일이라 운영 Lambda 결과는 아닙니다. 포트폴리오 문장을 그에 맞게 고치거나 운영 썸네일로 다시 재겠습니다.

**Q25. 가로·세로는 누가 정하나요?**
> 클라이언트가 기록 생성 요청에 넣어 보냅니다. 서버는 이미지를 열어보지 않으니 검증하지 않습니다. (`ActivityRecordReqDtoV2` 이미지 DTO)

**Q26. 큰 파일을 악의적으로 올리면?**
> presigned PUT이라 크기 제한이 없습니다. Lambda가 메모리나 타임아웃에 걸려 실패하고 DLQ로 가니 서버는 영향이 없지만, 비용과 저장 공간 문제는 남습니다. presigned POST의 `content-length-range`로 막는 게 개선점입니다.

**Q27. 원본은 왜 계속 보관하나요?**
> 나중에 다른 크기가 필요할 때 다시 만들 수 있어야 해서입니다. 자동 만료 규칙이 정상 파일까지 지우는 게 확인돼 전부 없앴습니다. 대신 기록 없이 올라간 고아 원본이 남는 문제가 있어 정리 배치가 필요합니다. (`lambda_s3_lifecycle.tf:1-7`)

**Q28. 측정하면서 어려웠던 점은?**
> 세 가지였습니다. 요청마다 32MB를 올리니 부하 발생기가 먼저 막혀서 설계를 바꿨고, AWS SDK가 더미 환경변수를 자격증명으로 집어서 인스턴스 역할만 쓰게 고쳤고, IMDS 홉 제한을 의심했다가 실제로는 제 확인 방법이 틀렸던 걸 측정으로 바로잡았습니다.

**Q29. CPU가 190~198%라는 건?**
> 도커의 CPU 퍼센트는 코어 하나를 100%로 셉니다. vCPU 두 개가 거의 다 찬 상태가 약 45초 이어졌다는 뜻입니다. (`stats-rate1.log`)

**Q30. 왜 이 문제를 "서버가 죽는다"고 표현했나요?**
> 프로세스가 죽은 건 아니고, 요청 26건이 OOM으로 500을 받았습니다. 정확히는 "요청 대부분이 메모리 부족으로 실패했다"가 맞습니다. JVM은 OOM 뒤에도 살아 있었습니다.

**Q31. 리사이즈 코드에 버그가 나면 어떻게 되돌리나요?**
> 지금은 이전 코드를 다시 배포하는 수밖에 없습니다. `prod` 별칭을 만들어 두긴 했는데, 리사이즈를 부르는 S3 트리거가 별칭이 아니라 최신 버전을 호출하고 있어서 별칭을 바꿔도 리사이즈에는 반영되지 않습니다. 버전 간 전환 리허설도 아직 못 했습니다. 되돌릴 수 있게 하려면 S3 알림 대상을 `함수명:prod`로 바꾸고, DLQ 연결도 별칭 기준으로 다시 걸어야 합니다. (`lambda_sqs.tf:34`, `lambda_alias.tf:10-19`, `README.md:124-131`)
- 꼬리: *그럼 별칭은 왜 만들었나요?* → 롤백 수단을 만들려는 의도였는데, 애플리케이션이 직접 부르는 커버 생성 함수 쪽만 별칭 호출로 연결했고, S3가 부르는 리사이즈 경로는 연결하지 못했습니다. 포트폴리오 문장도 그에 맞게 고치겠습니다.
