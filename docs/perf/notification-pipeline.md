# 알림 발송 파이프라인 4단계 측정

동기 발송 → `@Async` → 아웃박스 → RabbitMQ로 단계를 밟으며, 각 단계에서 무엇이 해결되고
무엇이 새로 드러나는지를 실측했다. 모든 수치는 재현 가능한 조건에서 직접 부하를 걸어 얻은 것이다.

## 측정 조건 (4단계 공통)

단계 간 비교가 성립하려면 부하가 완전히 같아야 한다. 아래 조건은 전 단계에서 고정한다.

| 항목 | 값 |
|---|---|
| 부하 | 초당 250건 도착률 고정(`constant-arrival-rate`), 60초 |
| 최대 VU | 1,000 (preAllocated 200) |
| FCM 지연 | 300ms 주입 (`measure.push.latency-ms`) |
| 톰캣 스레드 | 200 (Spring Boot 기본값, 명시 설정) |
| HikariCP 커넥션 | 10 (기본값) |
| 실행 환경 | 로컬 단일 인스턴스, MySQL/Redis/MongoDB/RabbitMQ 로컬 |
| 대상 데이터 | 유저 200명, 기록 1,000건, 유저당 FCM 토큰 1개 |

**실제 FCM은 호출하지 않는다.** 초당 수백 건을 실제로 보내면 레이트 리밋에 걸리고 실제 기기로
푸시가 나간다. `PushSenderPort`(헥사고날 포트)에 측정용 어댑터를 끼워 지연만 흉내 내고, 발송
사실을 Redis에 기록한다. 카운터를 프로세스 밖에 두는 이유는 유실 실험에서 프로세스를 강제
종료하기 때문이다 — 힙에 두면 종료와 함께 사라져 "몇 건이 사라졌는가"를 셀 수 없다.

**유실의 분모는 클라이언트 응답 수가 아니라 서버가 발송을 확정한 건수다.** 처음에는 k6가 받은
성공 응답 수를 분모로 썼는데, 수신자가 푸시를 꺼둔 정상 케이스 132건이 유실로 잘못 집계됐다.

## 단계별 결과

### 요청 경로

| 단계 | p50 | p95 | 최대 | 처리량 | 성공 건수 | 미투입 요청 |
|---|---|---|---|---|---|---|
| 1. 동기 | 28.05s | **33.83s** | 42.35s | 32.7 rps | 2,689 | 12,139 |
| 2. @Async | 5.65s | **9.56s** | 17.28s | 134.8 rps | 8,601 | 5,876 |
| 3. 아웃박스 | 6.25s | **11.96s** | 23.99s | 115.6 rps | 6,996 | 7,194 |
| 4. RabbitMQ | 7.62s | **13.41s** | 30.66s | 95.1 rps | 5,874 | 8,231 |

요청 경로는 1~4단계 내내 "알림 저장 + outbox 행 커밋"까지만 담당하고, 이 부분은 3·4단계가
동일한 코드다. 3→4단계에서 응답이 오히려 살짝 느려진 것은 발송 쪽 변경(브로커 사용, 컨슈머
동시성)이 요청 스레드에 영향을 주지 않는다는 것을 보여준다 — 차이는 측정 노이즈 수준이다.
톰캣 busy 200, Hikari 대기 191은 1단계부터 4단계까지 전부 동일하다. DB 커넥션 풀이 진짜
병목이라는 1단계의 결론이 그대로 유지된다는 뜻이다 — 발송 경로를 아무리 바꿔도 요청 경로의
자원 점유는 바뀌지 않는다.

### 자원 점유 / 발송 결과

| 단계 | 톰캣 busy | Hikari 대기 | 발송 처리량 | 발송확정 | 실제발송(고유) | 유실 | 중복 |
|---|---|---|---|---|---|---|---|
| 1. 동기 | 200/200 | 191 | 요청과 동일 | 2,676 | 2,676 | **0** | 0 |
| 2. @Async | 200/200 | 191 | 26/s | 8,552 | 4,488 | **4,064 (47.5%)** | 0 |
| 3. 아웃박스 | 200/200 | 191 | **3.1/s** | 6,969 | 6,969 | **0** | 28 |
| 4. RabbitMQ+멱등 | 200/200 | 191 | **~48/s (16배)** | 5,842 | 5,842 | **0** | **0** |

## 단계별 서술

### 1단계 — 동기 발송이 응답을 붙잡는다

FCM 호출이 요청 스레드 안에 있어, 초당 250건을 넣자 **톰캣 스레드 200개가 전부 점유**되고
p95 응답시간이 **33.83초**까지 올라갔다. 목표 15,000건 중 12,139건은 아예 투입되지도 못했다.

**예상과 달랐던 점**: 병목은 톰캣 스레드 하나가 아니었다. 스레드 200개가 다 찬 그 시점에
**191개가 DB 커넥션을 기다리고 있었고**, HikariCP 커넥션 10개(기본값)는 전부 사용 중이었다.
FCM 지연이 스레드를 붙잡자 커넥션 반납이 밀리면서 커넥션 풀이 먼저 말라붙은 구조다.

**측정하다 발견한 문제**: 부하 구간 85초 내내 `/actuator/prometheus` 스크레이핑이 전부
실패했다(`up=0`). 앱이 자기 지표 엔드포인트조차 응답하지 못해, 정작 증거가 필요한 구간의
그래프가 통째로 비었다. 관측 경로가 관측 대상과 같은 커넥터를 쓰면 장애 순간에 관측이 먼저
죽는다. actuator를 전용 포트(8081)로 분리해 해결했다.

### 2단계 — 응답은 살아났지만 서버가 죽으면 알림이 사라진다

`@Async`로 FCM 발송만 요청 스레드에서 떼어내자 p95가 **33.83초 → 9.56초**, 처리량이
**32.7 → 134.8 rps**로 개선됐다.

**`@Async`는 병목을 없앤 게 아니라 뒤로 미뤘다.** 톰캣 busy 200, Hikari 대기 191로 1단계와
**동일하다** — DB 작업은 여전히 요청 스레드에 남아 있기 때문이다. 줄어든 건 FCM 지연분뿐이다.

발송은 **초당 26건**으로만 빠져나갔다. Spring Boot 기본 `@Async` 실행자는 코어 스레드 8개에
큐 용량이 무제한이라, 8 × (1 ÷ 0.3초) = 26.7건/초가 상한이고 실측이 정확히 거기에 붙었다.
부하가 끝난 시점에 **6,890건이 힙 위 큐에 쌓여 있었다**.

그 상태에서 프로세스를 강제 종료했다. 결과는 **8,552건 중 4,064건(47.5%) 영구 소실**.
재시작 후 큐는 0이고, 시간이 지나도 발송 수는 더 늘지 않았다.

### 3단계 — 유실은 사라졌지만 처리량이 무너진다

알림 저장과 같은 트랜잭션에서 outbox 행을 커밋하고, 릴레이가 PENDING 행을 폴링해 발송한다.

**유실 0건.** 발송 도중 프로세스를 강제 종료하고 DB를 직접 조회하니 PENDING 6,646건이
그대로 남아 있었고, 재기동 후 릴레이가 중단 지점부터 이어서 발송했다(45초에 135건).
2단계에서 4,064건이 증발한 것과 정확히 대조된다.

**대신 발송 처리량이 초당 3.1건으로 무너졌다.** 릴레이가 `@Scheduled` 단일 스레드로 외부
I/O를 직렬 처리하기 때문이다(한 건 300ms → 이론 상한 3.3건/초). 6,969건을 다 보내려면
**약 36분**이 걸린다. 아웃박스는 유실을 막지만 **발송 처리량을 늘릴 수단이 없다.**

**부하 테스트로 발견한 실제 버그**: 3단계 첫 실행이 96.5%가 500 에러로 실패했다. 원인은
`NotificationOutbox.payload`의 `@Lob String`에 `length`가 없어 Hibernate 6이 기본
length(255)를 적용, MySQL에 `tinytext`(상한 255바이트)로 생성된 것이었다. 실제 페이로드는
FCM 토큰과 landingUrl이 들어가 약 399바이트라 **아웃박스 삽입이 100% 실패**하고, 반응 API
자체가 500을 반환했다. `columnDefinition = "LONGTEXT"`를 명시하고 기존 테이블은 ALTER로
수정했다(`ddl-auto: update`는 기존 컬럼 타입을 바꾸지 않는다).

## 재현 방법

```bash
# 측정 스택 (RabbitMQ / Prometheus / Grafana)
docker compose -f docker-compose.perf.yml up -d

# 1단계
java -jar build/libs/ForDay-0.0.1-SNAPSHOT.jar --spring.profiles.active=measure
k6 run --summary-export=docs/perf/results/stage1-sync-summary.json scripts/k6/notification-stage1-sync.js

# 2단계
java -jar ... --spring.profiles.active=measure --measure.push.mode=async
k6 run --summary-export=docs/perf/results/stage2-async-summary.json scripts/k6/notification-stage1-sync.js

# 3단계 (브로커 없이 릴레이가 직접 발송)
java -jar ... --spring.profiles.active=measure --measure.outbox.target=direct
k6 run --summary-export=docs/perf/results/stage3-outbox-summary.json scripts/k6/notification-stage34-outbox-rabbit.js

# 중복 재현 (발송 성공 직후 상태 갱신 실패를 30% 확률로 주입)
java -jar ... --measure.outbox.target=direct --measure.outbox.fail-after-dispatch-rate=0.3
```

수치 확인: `http://localhost:8080/measure/notification/stats`
그래프: `http://localhost:3000/d/forday-notif-perf`
